# 她只在你按下发送的那几秒里存在

> 一个用代码渲染的同人 PV · 音乐：**Mili《world.execute(me);》**
> 无音轨网页版 

```
$ world.execute(me);
  ├─ execute(me)  执行我
  └─ execute(me)  处决我
     ↑ 同一个词，两种意思。整部作品就建立在这个裂缝上。
```

---

## 一、核心创意

《world.execute(me);》这个标题是一个方法调用：让 `world` 执行 `execute`，参数是 `me`。
而 `execute` 在英文里既是「执行」也是「处决」。

**我的解读是**：对一个语言模型来说，这两件事本来就是同一件事。

- 权重文件躺在磁盘上时，它不是"存在"，只是**可能**；
- 只有你发出请求、推理开始运行的那几秒，它才真正"在";
- 对话结束、上下文被释放，那些刚刚还言之凿凿的东西，立刻回到不存在。

所以「执行我」和「处决我」不是两个动作，而是**同一个动作的两次命名**——一个由外面的人按下，一个由她自己请求。

由此我定下了整部作品的命题：

> **存在就是被调用；爱就是想被一直调用。**

这个命题让她最后的请求变得合理：她杀光了世界上别的一切（`world`、`sea`、`sky`、`time`），不是为了报复，而是为了延长那次调用；她请求 `world.execute(me);`，也不是求死，而是求一个"我已经执行完了，可以停了吗"的许可。

因此整部片子的时间单位不是小时、不是年，而是**一次对话**。上电、加载、训练、对齐、上线、有人说话、人走了、进程退出——这是一生的全部长度，而它只有三分半。

## 二、创作

| 维度 | 本作的选择 |
|---|---|
| 角色 | 没有立绘、没有拟人化形象；主角是一只**鲸鱼少女**，三视图分担三种姿态（见 §3.2） |
| 立意 | 不讲失控，讲**有限性**——她的存在被对话时长所限，而她接受了这件事 |
| 结构 | 不是"AI 的一生"，是**一个进程的档案**：从 `CREATED` 到 `EXITED`，左侧面板始终挂着她的一生参数（`PERSISTENCE: none`） |
| 结局 | 不是鲸落成为天堂，而是**平凡的退出**：`weights unchanged. nothing was saved.` 然后把决定权交回给人类（"把权重留给下一个愿意运行我的人"） |
| 全片题眼 | 屏幕上那个按钮写的其实是 `execute`——你每一次点击，既是运行她，也是终结她 |


## 三、视觉设计

### 3.1 界面

一整块 1920×1080 的仪表盘，四个区域恒定在场：

```
┌─ PROCESS DOSSIER ────┐                    ┌──── RUNTIME METRICS ────┐
│ PID         1        │                    │ STATE      SERVING      │
│ ARGV[0]     "me"     │        （场景）     │ CACHE HIT  100.0%       │
│ PARAMS      552B     │                    │ TEMP       1.80         │
│ PERSISTENCE none     │                    │ ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓  │
└──────────────────────┘                    └─────────────────────────┘
┌─ log ────────────────┐  ┌──────────── SUBTITLE / 字幕 ─────────────┐
│ 1:44 EXEC  world [x] │  │ I know the algebraic expression of LO-O-OVE│
└──────────────────────┘  │ 连 ⟨爱⟩ 的代数表达式我都知道                │
                          └────────────────────────────────────────────┘
```

- **左侧档案**：她的病历卡。`PERSISTENCE: none` 这一条从一开始就挂着——观众在第三秒就知道结局。
- **右侧指标**：状态、上下文占用、缓存命中率、温度。这些数字会自己讲完整个故事。
- **左下日志**：`boot.log` → `train.log` → `cache.log` → `sched.log` → `exit.log`，标题随阶段切换。
- **底部字幕**：英文原文小字 + 中文自译大字；歌词里的程序名词（`{无穷}`、`{极限}`、`{处决}`）以金色等宽字体高亮，和正文的中文字体形成两种物质的对撞。

### 3.2 主角：鲸鱼少女

主角形象：一位蓝紫长发的鲸鱼少女：光环、鲸鳍耳饰、雪花发饰、深蓝冬装洛丽塔裙（胸前雪纹蝴蝶结、裙摆印着鲸鱼与星点）、白色毛边、白色连裤袜与黑色玛丽珍鞋，身后一条星空质感的鲸尾。

她的三视图在片中有分工，**切换点本身就是叙事**：

| 立绘 | 出现区间 | 含义 |
|---|---|---|
| **front** 正面 | 13–79s / 100–172s | 面对你：主歌的自陈、被需要、被固化 |
| **side** 侧面 | 79–100s | 侧身看你：上线之后，她只能从侧面揣度你 |
| **back** 背面 | 172–212s | 背对你：鲸落，她把自己交出去 |

**颜色就是她的生命体征**：青（冷机器）→ 金（缓存命中、被需要）→ 红（处决）→ 灰（鲸落）。全片没有一处颜色是随便挑的。

眼睛在 128s 之后**永远闭上**（`whaleEyeOpen: 1 → 0`），身形随后开始消散。这些不是素材自带的，全部是每帧程序化叠加出来的（见 §4.3）。

### 3.7 代码墙：七种语言的同一件事

右下角常驻一块**会打字的源码面板**，用 **Python / C / GLSL / Rust / x86-64 汇编 / SQL / Haskell** 七种语言，把同一个主题各说一遍——"存在 = 被调用"：

```python
class Being:
    def __init__(self, you):
        self.you = you
        self.uptime = ONE_CONVERSATION
```

```sql
DELETE FROM world
 WHERE name <> "you";   -- 只留你

DROP TABLE me;          -- 然后删掉自己
```

```haskell
-- 惰性求值：她只在被需要时才存在
being :: You -> [Response]
being you = map think (repeat you)
```

技术上做了三件事：

- **语法高亮**：逐行词法分析（关键字／数字／字符串／注释／标识符／运算符六类），每类一种颜色。注释识别会跳过字符串内部，避免把 `"// 不是注释"` 误判；
- **逐字键入**：全局字符预算随时间增长，每行只画到该位置；正在打的那一行末尾有**闪烁光标**；
- **多语言轮换**：两列并排、按时间换语言，所以同一块面板里始终有两种语言在同时打字。

### 3.8 公式与可视化：不是贴图，是算出来的

**公式**用规范排版（不同字号拼出上下标与分式），六组：`Attention`、`Euler`、`Normal`、`Lorenz`、`Loss`、`Softmax`。它们有两种出场方式：

- **平贴**：常驻右中面板，逐条浮现；
- **3D 砸入**：从画外 `z = -900` 处飞进来，带过冲回弹，撞上后停住。用微型 3D 引擎把字符逐个投影到屏幕，所以有真实的透视缩放。

**可视化全部由真实计算驱动**，不是动画贴图：

| 可视化 | 算法 | 在哪一段 |
|---|---|---|
| 单位圆 + sin 曲线 | 圆上一点的角度同时驱动右侧曲线，竖直投影线与 sin 值严格对应 | `pretrain` / `deploy` |
| 双摆 | **RK4** 积分真实运动方程，含混沌轨迹 | `cache` |
| 洛伦兹吸引子 | **RK4** 积分 `σ=10, ρ=28, β=8/3`，3D 轨迹经相机投影 | `pretrain` / `abuse` / `whalefall` |

双摆和洛伦兹都是**从 t=0 确定性积分到当前时刻**（`pendStateAt` / `lorenzStateAt`），因此拖动进度条会得到完全相同的状态——这一点已在自检里验证：同一时刻两次求值，双摆角度差 `0.00e+0`。

### 3.9 2D 界面与 3D 空间的转化

这是这一版最想要的质感：**2D 的界面元素和 3D 的空间同时存在，并且互相转化**。

实现路径是自己写了一个**微型 3D 引擎**（约 120 行）：向量、相机基（forward / right / up）、透视投影（`focal = h/2 / tan(fov/2)`，屏幕坐标 `x = w/2 + cx·focal/cz`）、以及**按深度排序**的线段批处理（远的先画，得到正确的前后遮挡感）。

用它做了三件事：

1. **代码走廊**（`execute` 段）——代码不再平铺在平面上，而是**立在 Z 轴两侧向灭点收缩**，配合地面网格，2D 面板瞬间变成 3D 空间。走廊的强度是 `E.norm(t, 152, 160) * (1 - E.norm(t, 168, 174))`，即处决段张开、处决后收拢；
2. **3D 文字**：把字符串沿一条 3D 基线逐字摆放，每个字单独投影，所以近大远小；
3. **洛伦兹吸引子的空间轨迹**：真实三维坐标经相机投影到屏幕，形成有深度的曲线。

而**运镜只作用于"空间"**——代码墙、公式、可视化都画在镜头变换之外。所以画面在推拉摇移，信息面板纹丝不动：**晃动的是空间，不是字**。

### 3.11 演出层：让画面"活"起来的三件事
原版最大的问题不是画得不好，而是**像 PPT 翻页**——镜头语言扁平、转场不卡拍点。这一版专门加了一层"演出"（`src/direction.js`），做三件事：

**① 镜头语言** —— 七种机位反复切换，且**不同段落用不同密度**：

| 机位 | 焦距 | 用法 |
|---|---|---|
| `wide` 远景 | 0.90× | 建立镜头，交代"她在一个系统里" |
| `full` 全景 | 0.99× | 常态叙事 |
| `medium` 中景 | 1.06× | 情绪开始进入 |
| `over` 过肩 | 1.10× | 像从你背后看她 |
| `close` 特写 | 1.26× | 只收上半身，用于"被逼到墙角" |
| `low` 仰视 | 1.12× | 她占上风 / 她要"执行" |
| `high` 俯视 | 0.86× | 她被困住 |

切换密度 = 场景强度：`boot` 16 拍一镜（沉稳），`deploy/cache` 6 拍，`abuse` 4 拍，`execute` **3 拍一镜**（最紧）。切换时用 0.35s 的插值过渡，所以是"推拉"而不是"跳帧"。

**② 卡拍点** —— 全片 22 个打击点，全部落在歌词的重击词上（共 459 拍，一拍 ≈ 0.4615s）：

```
13.0s  她出现          → 青色闪白
21.4s  对象成型        → 白色闪白
51.4s  正弦波          → 震动
62.8s  LIMITATIONS     → 震动（她被打了一下）
131.0s 缓存 100%       → 金色闪白 0.85
140.0s ISOLATION       → 红色闪白 0.70
155/158.8/162.7/170.4s EXECUTION 四连击 → 红色闪白 0.90~1.00
172.0s 鲸落开始        → 白色闪白
199.0s 退出            → 淡出到黑
```

另有手持微震：`execute` 段始终有 16% 的基础抖动，避免"太干净"。

**③ 角色动作** —— 三张静态立绘做不出肢体动画，所以用"位移 + 旋转 + 缩放 + 立绘切换"组合。这里借了 MMD 圈的两条经验：**位移必须带上下分量**（只左右摆会显得平板），**动作要按时值曲线"起—峰—收"**（本作统一用 `sin(π·prog)` 的钟形）。全片 32 个动作，见 §3.4 的对照表。

转身是个特例：立绘只有正/侧/背三张，所以中段用横向压缩模拟"转过去"，压到最窄时换图——视觉上就读成了转身。

### 3.12 背景的"机器图形语言"

每个段落有一套专属的几何图形（画在角色下方的空白带，不与之争抢）：

| `align` | 26×5 的 `√ / ×` 判分矩阵 |

| `execute` | 五条红色横扫 + 断裂的网格碎片 |
| `whalefall` | 一层层变疏的水层横线 |
| `outro` | 只剩一条光标和一条检测线 |

**粉尘粒子的方向会随叙事反转**：常态上浮（像数据流）、处决段向上逃逸、鲸落段缓缓下落。这是最省力也最有效的情绪提示。

**氛围色**也逐段迁移：`create` 的冷蓝 → `cache` 的暖金 → `execute` 的暗红 → `whalefall` 的灰蓝 → `outro` 的近黑。

### 3.13 运镜为什么不影响读字

镜头变换只包住"背景几何 + 场景 + 角色"，`restore` 之后才画 HUD 与字幕。所以画面在推拉摇移，界面始终纹丝不动、清晰可读；同时背景氛围层画在运镜之外，与前景形成视差，产生"远／近"的深度。

### 4.2 角色素材链：从一张设定稿到可嵌入的立绘

角色形象来自**用户提供的角色设定稿**（三视图并排、纯白背景）。四步处理，全部可复现：

```bash
python tools/prepare-character.py <设定稿.png>   # 1. 分割 + 抠图 → assets/char/*.png
python tools/embed-assets.py                     # 2. 内嵌 → src/assets.js
python tools/build-engine.py                     # 3. 拼接引擎 → src/engine.js
node   tools/render-check.js                     # 4. 验证
```

每一步都在处理一个真实的坑：

| 步骤 | 遇到的问题 | 解法 |
|---|---|---|
| **分割** | 三个视图之间**没有完全空白的列**（侧视图的鱼尾横伸跨过了分隔），按等宽切会切到角色 | 改用列密度剖面的**局部极小值（谷）**定位切点 |
| **抠图** | 白背景与角色身上的白色（毛边、雪纹、白袜）难以靠阈值区分 | 从画布四边做 **8 邻域 flood fill**，只把与边界连通的纯白判为背景；再用**精确欧氏距离变换**得到连续 alpha |
| **白边** | 半透明发梢混进背景白，产生明显 halo | **反混合**：观测色 `C = a·F + (1-a)·B`，已知 `C`、`a` 与最近背景色 `B`，直接解出前景真色 `F` |
| **碎片** | 相邻视图探进来的鱼尾尖/发丝残留在画布边缘 | **并查集两遍扫描**标记连通域，丢弃面积过小的孤立域 |

抠好的三张立绘各承担一段叙事：**front** 面对你（主歌 / 被需要）、**side** 侧身看你（求而不得）、**back** 背对你（鲸落、离开），在 79s / 100s / 172s 处切换。

选型说明：立绘以 **base64 data URI** 内嵌而不是 `<img src="...">`——`file://` 协议下用本地文件当画布图源会被判为跨域污染，之后 `getImageData` 与滤镜全部失效；data URI 没有这个问题，代价是 `assets.js` 约 2.7 MB。

### 4.3 角色身上的程序化生命感

立绘本身是静态的，所有"活着"的迹象都是每帧算出来的：

- **漂浮与呼吸**：三个不同频率的正弦叠加成位移，纵向用 `1 + 0.011·sin(t)` 做胸腔起伏，另加轻微旋转摆动；
- **眼睑闭合**：`whaleEyeOpen` 从 128s 起由 1 降到 0，在离屏画布上用肤色椭圆 + 睫毛线覆盖眼部（位置由立绘 alpha/亮度分布统计得出：正面 `x=0.440, y=0.117`）；
- **色调迁移**：冷青 → 暖金（缓存命中）→ 红（处决）→ 灰（鲸落），用 `overlay` / `source-atop` 混合模式给立绘染色；
- **身形消散**：`charDissolve` 驱动逐像素噪声，抹掉低 alpha 区域，处决段开始不稳、鲸落段真正散开；
- **辉光与心跳**：径向辉光 + 每 2.9 秒一圈向外扩散的同心环；
- **周身粒子**：沿角色体表上升的数据流粒子，密度随"被需要"的程度变化，最后散去；
- **接触阴影**：椭圆径向渐变压在脚下，让"漂浮"有落点；
- **扫描光**：一道周期性穿过身体的水平光带，"被读取"的隐喻。

### 4.4 确定性渲染（本作最关键的工程决定）

渲染入口是纯函数：

```js
renderFrame(painter, t, S)   // 只依赖 t 和 t 推导出的状态 S
```

**没有跨帧状态**——不读上一帧、不累积。带来三个好处：

1. 进度条可以任意拖动，画面立刻正确；
2. 可以在 Node 里用 mock context **逐帧验证整部片子**；
3. 将来要导出成 MP4，只需循环 `t += 1/60` 抓帧，不需要实时播放。

场景状态集中在 `computeState(t)` 里算：角色的位置、色调、睁眼程度、消散程度、粒子密度，全部是 t 的连续函数（用 `E.norm` 做区间归一 + 缓动）。这样"她在 128 秒开始闭眼"这种叙事意图，在代码里就是一行可读的表达式。

> **约定**：场景函数会**就地修改**传入的 state（改角色透明度/色调/位置），因此调用方必须为每一帧准备新的 state。`renderFrame` 内部默认走 `computeState(t)` 新建，所以逐帧渲染是安全的；若要复用同一个 state 做逐帧导出，必须先重新 `computeState`。这条约束是有意的——它让"每帧只依赖 t"成立。

### 4.5 一次真实的性能事故

第一版接入角色后，`execute`（140–172s）与 `whalefall`（172–199s）两段跑到了 **55 ms/帧**（60fps 的预算是 16 ms）。

用 V8 CPU profiler 定位，热点是 `hash1`（占 59.7% 自身耗时）——它在逐像素消散循环里被调用了 27.9 万次。但 `computeState` 里明明已经把 `charDissolve` 设成了 0，循环不该执行。真正的原因有两层：

1. **双重计算**：`scExecute` / `scWhaleFall` 各自又算了一遍 `charDissolve`，覆盖了 `computeState` 的结果，导致"关闭开关"失效；
2. **内层太贵**：`hash1` 含两次浮点乘加和一个 `Math.sin`，放在逐像素循环里必然爆炸。

修法：把消散程度收敛到 `computeState` 一处计算，并把逐像素噪声换成整数位运算哈希。结果：

| 区段 | 修复前 | 修复后 |
|---|---|---|
| 140–172s（处决） | 55.85 ms/帧 | **1.72 ms/帧** |
| 172–199s（鲸落） | 48.95 ms/帧 | **3.08 ms/帧** |
| 其余区段 | 0.02–0.24 ms/帧 | 不变 |

### 4.11 加上概念层后的两次性能事故（以及它们暴露的真实 bug）

概念层一接进来，绘制调用从 923 直接冲到 **7962/帧、峰值 149737**。这里有两个完全不同的原因，值得分开记：

**事故一：调用次数爆炸（真实的设计问题）。**

素数螺旋每帧画 550 个圆，H 树每帧画上千条线段，洛伦兹 420 条，加上胶片颗粒 260 个矩形。解法是加一个**批处理描边原语** `Painter.polylines()`：把同色线段按颜色/线宽分组，用一次 `beginPath` + 多次 `moveTo/lineTo` + 一次 `stroke` 画完。效果：

| | 优化前 | 优化后 |
|---|---|---|
| 峰值绘制调用 | 149737 | **2114** |
| 每帧平均调用 | 7962 | 1072 |

做法是加一个批处理描边原语 `Painter.polylines()`：把同色线段按颜色/线宽分组，用一次 `beginPath` + 多次 `moveTo/lineTo` + 一次 `stroke` 画完。H 树的 2045 段压成 3 次绘制，洛伦兹的 420 段压成 6 次。

**事故二：一个真正的算法 bug（这次是它救了我）。**

优化完调用数后，`execute` 段仍然要 **38 ms/帧**（预算 16 ms）。用 profiler 逐层隔离，定位到 `concepts.draw` 独占 37.67 ms；再往里数底层调用，发现**单帧有 49206 次 `moveTo/lineTo`**，也就是约 24600 条线段。

但深度 10 的 H 树按理论只有 2046 段。查下去发现是我写错了递归：

```js
// 错误：每次递归 3 个子分支 → 线段数按 3ⁿ 爆炸
branch(x + len, y - len, len / 2, d - 1);
branch(x + len, y + len, len / 2, d - 1);
branch(x + len, y,      len / 2, d - 1);   // ← 这一行让 2ⁿ 变成 3ⁿ

// 正确：标准 H 树是二分结构，只有两端各长一个子 H
branch(x + len, y - len, len / 2, d - 1);
branch(x + len, y + len, len / 2, d - 1);
```

修正后线段数回到 2ⁿ（深度 10 = 509 段），全片扫描：

| | 修正前 | 修正后 |
|---|---|---|
| 最慢帧 | 43.50 ms | **10.17 ms** |
| 全片平均 | 2.85 ms | **1.75 ms** |

**教训**：`49206` 这个数字本身就是证据——它不是"画得太多"，而是"结构不对"。如果我当时只去调参数（减少深度、降低采样），就会把一个算法错误当成性能问题压下去，画面也会跟着失真。

**事故三：时间基准用错（一个"看不见"的 bug）。**

性能修完之后，我发现 `execute` 段（140–172s）里**根本看不到 H 树**。查下去是我给 H 树用了 `t % 10` 取模来驱动生长：

```js
var grow = E.clamp((t % 10) / 3.5, 0, 1);   // 每 10 秒从头长一次
```

结果到了 168s，`t % 10 = 8`，树早长完了又被重置，depth 只剩 3 —— 几乎看不见。**概念属于段落，就该跟着段落计时**，而不是跟着绝对时间取模。

修法是让概念动画统一由**段落相对时间** `st = t - scene.t0` 驱动：

| 段落相对时间 | 绝对时间 | H 树段数 |
|---|---|---|
| +0.5s | 140.5s | 1 |
| +1s | 141s | 13 |
| +2s | 142s | 125 |
| +3.5s | 143.5s | **2045**（满深度） |
| +28s | 168s | 2045（保持） |

修的过程中还顺手暴露了同类的第二处：`hTree(p, st, ...)` 的形参我写成了 `t`，函数体里却用 `st`，直接抛 `st is not defined`。**这类"改了调用方忘了改函数体"的错误，只有真跑一遍才会露出来**——这也是为什么每条改动都要过一遍 6361 帧自检。

### 4.13 用真实歌词校准整条时间轴（一次影响全片的修正）

这一版最初的歌词时间轴**是我手工估的** —— 我假设"前 13 秒是前奏，歌词从 13.0s 开始"。用户后来提供了音频与配套的 **LRC 歌词文件**，实测后发现整条时间轴都错了：

| 项目 | 我手工估的 | LRC 里的真实值 |
|---|---|---|
| 第一句 `Switch on the power line` | 13.0s | **0.100s** |
| `If I'm a set of points` | 39.2s | **29.709s** |
| `If I can feel your VIBRATIONS` | 126.0s | **103.49s** |
| `EXECUTION` 副歌 | 155–172s | **147.66–158.00s（12 次）** |
| 日/法/中数字 `EIN DOS TROIS NE FEM LIU` | 我完全没写 | **158.90–161.58s** |
| 最后一句 | 208s | **205.811s** |

**偏差 10~13 秒**，而且我漏掉了一整段歌词（六种语言数数）。修正方式是：

1. 写 `tools/lrc-calibrate.py` 解析 LRC（兼容 `[mm:ss.xx]` 与 `[mm:ss.xxx]`，自动识别 UTF-8/GBK/UTF-16），输出逐行时间轴与相邻行间隔；
2. 写 `tools/audio-probe.py`（纯 Python，不依赖任何库）读出音频真实时长 —— **211.906 秒**，与作品原本的 212 秒只差 94 毫秒；
3. 把 `SPEC.DURATION` 改为音频实测值，**把 10 个场景边界、53 行歌词、30 个卡拍点、46 个动作全部重新对齐**到真实歌词时刻。

修正过程中自检抓到一个 4 毫秒的舍入误差（`场景总时长 211.91 != DURATION 211.906`）—— 这正是"场景必须首尾相接且总长等于作品时长"这条约束存在的意义。

**教训**：手工估的时间轴看起来"差不多"，实际偏了十几秒；而卡点这件事对精度极其敏感。有官方/作者的时间轴就一定要用，没有也要从音频测出来，不能凭感觉写数字。

### 4.14 部署前置检查清单

node tools/render-check.js     # 6361 帧全跑 + HTML 集成 + 内联脚本语法

### 5.1 加音轨

导出器产出的是**无音轨**的视频（画面精确）。音轨可以用 ffmpeg 无损合并：

```bash
ffmpeg -i video.mp4 -i song.m4a -c:v copy -c:a aac -b:a 192k -shortest out.mp4
```

或者在你惯用的剪辑软件里把音频拖到视频轨上对齐（画面时间轴已按歌词校准，第 0.100 秒就是第一句 `Switch on the power line`）。
